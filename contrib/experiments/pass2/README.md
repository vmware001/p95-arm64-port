# contrib/experiments/pass2 — is there headroom in the pass-2 FFT kernel?

**Verdict: no. On the RK3528 / Cortex-A53 the pass-2 kernel is already running at
the machine's instruction-throughput limit. Three bit-exact data-movement /
scheduling variants were built and measured end-to-end: all were within noise
of the baseline (+0.4…+0.5%, i.e. slightly slower). No change was adopted.**

Full report: [`REPORT-pass2.md`](REPORT-pass2.md). This README is the summary.

## Why pass-2 was the target

Attributing every PC sample of a full 16K multiply (5961 samples, 18000
multiplies, exp 264169) reproduces the calibrated profile:

| 16K (M264169) | % |  | 400K (M7831391) | % |
|---|---|---|---|---|
| pass-1 `xfft_r4_16K_np_8_4_CORE_i` | 49.7 |  | pass-1 `xfft_r4dwpn_400K_1280_4_CORE_i` | 51.6 |
| **pass-2 `r4_pass2_8_levels_complex`** | **33.7** |  | **pass-2 `r4_pass2_1280_levels_complex`** | **38.7** |
| `xi2CORE` | 12.7 |  | `xi3CORE` | 8.8 |
| `xpass2_r4_8_levels` | 2.9 |  | `xpass2_r4_1280_levels` | 0.7 |

## Why there is nothing left to win

`r4_pass2_8_levels_complex` = 4096 B, 1024 instructions, 8 small loops. The hot
butterfly loop is **103 instructions**: 62 double-precision vector FP ops
(16 fadd, 16 fsub, 12 fmul, 12 fmla, 6 fneg) + 34 memory ops (16 `ldr q`,
16 `str q`) + 1 branch. Clang already emits:

- **no register spills**, no scalar fallback on the FP path,
- loads scheduled ahead of their uses, `ldp`/`stp` where the addressing allows.

Cost accounting: 16 blocks x 256 butterflies = 4096 calls per multiply,
≈ **179 cycles/call, IPC ≈ 0.55**, i.e. ≈2.06 cycles per instruction.
A synthetic replica of the same instruction mix (all L1-resident) runs at
**2.08 cycles/instruction** — the real kernel is *at* that limit. The 4 KB
per-block working set means there is no cache-miss cost left to recover, and
the FP pipe alone would need 325K cycles vs the ~730K actually used. Getting
more ILP would need ~60 vector registers to interleave two butterflies;
ARMv8.0 has 32.

## Variants built and measured (all bit-exact)

Measurement: farm SIGSTOPped, pinned to cpu2, interleaved A/B, medians of
3 reps x 5 runs (16K) / 6 runs (400K).

| spec | 16K timeA (ms) | digest |
|---|---|---|
| `bench_base` (production `mprime-mc4` gwnum) | **1.0637** | `9eb6e6aa156860ac` |
| harness v0 (same source, in-binary control) | 1.0703 | `9eb6e6aa156860ac` |
| v1 — 4-trip inner butterfly loops unrolled x2 | 1.0760 (+0.5% vs v0) | `9eb6e6aa156860ac` |
| v4 — restored twiddle `prfm pdl1keep` (the x86→C conversion had turned every prefetch into a no-op) | 1.0752 (+0.4% vs v0) | `9eb6e6aa156860ac` |
| v5 — `__restrict` butterfly pointers | byte-identical binary to v0 | not timed |

400K: baseline 35.091 ms, v0 35.289, v1 35.227 — no gain, no regression; digest
`ae78e849c76aef67` everywhere.

Two further variants (32/64-trip unrolling, generated by script) were discarded
as *invalid experiments*: the generator mis-modelled a 2-line loop body and
dropped a twiddle advance (digest differed), so they prove nothing either way.

## The only remaining lever, and why it is closed

Fewer DP operations (radix-8 instead of radix-4, fewer twiddles) would break
the 1–2% ceiling — but it changes the rounding and therefore the FFT safety
margin, and it is a large porting job: the x86 radix-8 kernels (`hg/hg*.mac`
→ `hg/hg*.c`) would have to be re-derived for aarch64. gwnum already ships
radix-8 "hg" entries for small one-pass FFT sizes and picks implementations by
its own benchmarking, so on this CPU it already decided radix-4 wins.

Note on the correctness gate: bit-exactness is not a rule that forbids new
algorithms — it is a *property* that any exact implementation automatically
satisfies (gwnum's FFT multiply must return the true integer, so two correct
implementations must agree bit for bit). The gate that matters is
[`../../validation/`](../../validation/README.md) layers 1–2 (GMP bit-exact
checks and known PRP answers). A radix-8 rewrite would be admissible *if* it
passes those; it is simply too large for the expected payoff.

## Bottom line

Three independent optimisation experiments on this box are now complete and all
three were ≈0%: FMA contraction (`-ffp-contract=fast`), hand-written NEON for
the pass-1 copy loops (`../asm-pass1/`), and pass-2 data-movement/scheduling
(this directory). The farm's real gains came from fixing a stale worker
(`Memory=768`, +33% throughput, see `../../farm/README.md`) — not from the
kernel. Further kernel work on ARMv8.0/Cortex-A53 should be considered closed.
